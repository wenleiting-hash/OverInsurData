## 一、背景与目标

### 1.1 系统定位

- **workOS**：海外保险数字化平台的主系统，CS（Client Server）软件，业务人员日常操作全部在 workOS 中完成。
- **保险公司管理子系统**：管理上游保险公司、产品、合作授权、资质、财务结算等。
- **渠道管理子系统**：管理下游分销渠道、入驻、合规、产品授权、佣金等。
- 两个子系统共用同一套后端服务与用户/权限体系（`auth_user` / 角色权限表），一套集成机制同时覆盖。

### 1.2 业务场景

业务人员在 workOS 开展**保单咨询**业务时，需要向两个子系统查询：

1. 符合条件的保险公司（官网、承保险种、准入资质、合作状态）；
2. 该保司已授权的保险产品（授权州、生效范围、在售状态）；
3. 产品核保规则要点。

一期由**我司业务人员**根据客户提供的投保基本信息（历史投保、客户基本信息、投保险种、产品意向等）发起查询；**一期不支持渠道商发起保单咨询**。

### 1.3 两种集成模式

| | 模式 A：SSO 独立入口 | 模式 B：业务环节接口调用 |
|---|---|---|
| 形态 | 浏览器跳转，人进入子系统页面操作 | workOS 后端调子系统接口，纯数据传递、无页面 |
| 身份 | workOS 自然人用户，需落用户表 | 系统级应用身份，不落终端用户 |
| 权限 | 按同步的用户角色权限控制菜单与操作 | 接口级固定只读范围 |
| 触发 | 用户主动从 workOS 跳转 | workOS 业务流程中自动调用 |
| 客户信息 | 不涉及 | 不传客户 PII，仅业务查询键 |

## 二、模式 A：SSO 独立入口

### 2.1 总体原则：权限先行、用户单向同步

1. 两个子系统先将**业务角色/权限目录**提供给 workOS；
2. workOS 创建用户并勾选子系统权限后，调用**用户同步接口**将用户与角色写入子系统；
3. 用户从 workOS 跳转时，子系统凭一次性 code 向 workOS 换取用户信息，按工号匹配**已同步账号**，签发本系统 JWT；
4. 同步方向为 **workOS → 子系统 单向**：子系统本地创建的用户不回写 workOS。

### 2.2 SSO 登录流程

```
业务人员          workOS                子系统前端              子系统后端
   │  点击子系统入口  │                       │                      │
   │───────────────▶│                       │                      │
   │                 │ 302 跳转              │                      │
   │                 │ /sso/callback?code=.. │                      │
   │                 │──────────────────────▶│                      │
   │                 │                       │ POST /api/auth/sso/  │
   │                 │                       │   exchange {code}    │
   │                 │                       │─────────────────────▶│
   │                 │  服务端校验 code、     │                      │
   │                 │  换取用户信息(工号/姓名)│                      │
   │                 │◀────────────────────────────────────────────│
   │                 │  返回用户信息          │                      │
   │                 │─────────────────────────────────────────────▶│
   │                 │                       │  按工号匹配账号、签发 │
   │                 │                       │  本系统 JWT           │
   │                 │                       │◀─────────────────────│
   │                 │                       │ 按角色权限进入系统    │
```

**关键要求：**

| # | 要求 | 说明 |
|---|---|---|
| A1 | 一次性 code | code 短时有效（建议 ≤ 60 秒）、使用一次即失效，URL 中不得出现姓名、角色等明文身份信息 |
| A2 | 后端换码 | code→用户信息的交换只在服务端进行（携带子系统 client 凭证），前端不接触 workOS 密钥 |
| A3 | 工号匹配 | 以 workOS 工号（`external_id`）匹配已同步账号；匹配不到则拒绝登录并提示"账号未同步，请联系管理员在 workOS 开通"，**不接受 URL 传入的 role** |
| A4 | state 防 CSRF | 跳转携带 workOS 生成的 state，回调时校验 |
| A5 | 会话 | 换发子系统自有 JWT（access + refresh），前端沿用现有会话存储机制；登出仅清除本系统会话 |
| A6 | 账号状态 | 已禁用用户（workOS 同步禁用或本地停用）拒绝换发 JWT |

> ⠂废弃方案：现有登录页 SSO Tab 中文档化的 `token/user/role/platform` 明文 URL 参数方案存在角色伪造提权风险，本期按 code 换发重做，该说明页同步替换。

### 2.3 用户/权限同步接口（workOS → 子系统）

**用途**：workOS 创建、变更、禁用用户时，将用户身份与其在两个子系统的业务角色同步写入。

**设计要点：**

| # | 要点 | 口径 |
|---|---|---|
| B1 | 同步方向 | 仅 workOS → 子系统；子系统本地账号不回写 |
| B2 | 触发方式 | 支持实时单条 upsert（建人/改人/禁用时）；是否需要定时批量对账由 workOS 方确认（见第六章） |
| B3 | 幂等 | 以工号为唯一业务键 upsert，重复推送不产生重复账号 |
| B4 | 同步内容 | 工号、中英文名、邮箱、部门、子系统角色清单、账号状态（启用/禁用）、来源标记 |
| B5 | 角色来源 | 角色必须是子系统权限目录中已存在的角色 key；未知角色整单拒绝并返回错误明细，不做部分写入 |
| B6 | 权限边界 | 同步仅写 `auth_user` + 用户角色关联；菜单/按钮/接口权限仍由子系统角色定义决定，workOS 不直接写权限点 |
| B7 | 鉴权 | 复用模式 B 的 API Key + HMAC 签名 + IP 白名单 |
| B8 | 本地账号 | `auth_method='local'` 的既有账号不允许被同步接口覆盖（工号撞号时返回冲突错误，人工处理） |

### 2.4 登录后可见范围

- SSO 用户进入子系统后，**菜单与操作权限完全按其同步的角色决定**，与本地用户走同一套权限体系，无独立菜单裁剪逻辑；
- 可覆盖保险公司管理、渠道管理两个子系统的全部页面（含只读或可写，由角色配置决定）；
- 用户管理列表中 SSO 账号显示认证方式徽章（SSO / workOS），且不提供本地密码重置入口。

### 2.5 离职与禁用

- **主路径**：以 workOS 同步接口推送的禁用状态为准，禁用后该账号无法换发 JWT，已签发 JWT 在 access token 有效期（当前 1 小时）到期后失效；
- **兜底**：SSO 换码时 workOS 返回用户已离职/不存在，同样拒绝登录；
- 是否需要"禁用即吊销未过期 token"（引入 token 黑名单/短有效期）列入待确认。

## 三、模式 B：保单咨询业务环节接口

### 3.1 场景

workOS 业务流程中（保单咨询录入环节）由 workOS 后端调用子系统查询接口，获得"保司 + 授权产品 + 核保要点"数据，嵌入 workOS 界面展示。**不跳转页面、不传递终端用户身份、不接收客户 PII。**

### 3.2 鉴权与安全

| # | 项 | 规格 |
|---|---|---|
| C1 | 应用凭证 | 为 workOS 签发 `appKey` / `appSecret`，secret 仅服务端持有 |
| C2 | 签名算法 | HMAC-SHA256；签名串 = HTTP 方法 + 请求路径 + `X-Timestamp` + `X-Nonce` + body 的 SHA-256 |
| C3 | 防重放 | `X-Timestamp` 与服务端时间偏差 ≤ 5 分钟；`X-Nonce` 一次性，服务端缓存去重（建议保留 10 分钟） |
| C4 | IP 白名单 | 服务端仅接受 workOS 出口 IP 网段（网段清单由对方提供） |
| C5 | 透传字段（可选） | `X-Operator-Id`（操作人工号）**仅写审计日志**，不参与鉴权与授权 |
| C6 | 传输 | 全程 HTTPS；建议生产环境加网络层访问控制 |
| C7 | 限流 | 按 appKey 限流（阈值待定，建议初始 60 次/分钟），超限返回 429 |
| C8 | 密钥轮换 | 支持 appSecret 轮换期（新旧双密钥并存），轮换流程由运维约定 |

**请求头约定：**

```
X-App-Key:    {appKey}
X-Timestamp:  {unix epoch seconds}
X-Nonce:      {uuid}
X-Signature:  {HMAC-SHA256 hex}
X-Operator-Id:{workOS 工号，可选，仅审计}
Content-Type: application/json
```

### 3.3 接口契约：咨询匹配

#### `POST /api/integration/v1/consultation/match`

按业务查询键返回"符合条件的保司及其授权产品"。

**请求体：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `line_of_business` | string | 是 | 险种代码（如 AUTO / HOME / HEALTH / SURETY 等，枚举对齐子系统产品险种字典） |
| `state` | string | 是 | 美国州二字码（大写，如 CA） |
| `product_code` | string | 否 | 指定产品编码；传则只返回该产品并校验其授权/在售状态 |
| `keyword` | string | 否 | 产品名称关键词（模糊匹配） |
| `customer_type` | string | 否 | `individual` / `commercial`，用于过滤产品适用客群 |
| `lang` | string | 否 | `zh-CN` / `en-US`，默认双语全量返回 |

**明确不传**：客户姓名、证件、联系方式、历史投保明细等任何客户 PII；客户信息留在 workOS 侧。

**过滤口径（全部满足才返回）：**

1. 保司合作关系有效：已签约/履行中，未终止、未过到期日；
2. 产品已通过该保司合作授权接入（合作产品关联在生效期内）；
3. 产品处于在售状态；
4. 产品在该州开放销售（州状态为可售、未暂停）；
5. 客群类型匹配（传入 `customer_type` 时）。

**返回内容三块：**

| 数据块 | 字段 |
|---|---|
| ① 保司准入资质 | NAIC、中英文名、简称、**官网网址**、Admitted 身份、AM Best / S&P 评级、合作状态、合作到期日、承保险种 |

**一期不返回**：渠道资质与渠道授权、佣金/费率/财务数据、保司联系人与合同文件。

**错误码约定：**

| HTTP | code | 场景 |
|---|---|---|
| 401 | `INVALID_SIGNATURE` | 签名缺失/错误 |
| 401 | `TIMESTAMP_EXPIRED` | 时间戳超窗 |
| 409 | `NONCE_REPLAYED` | nonce 重复 |
| 403 | `IP_NOT_ALLOWED` | 来源 IP 不在白名单 |
| 429 | `RATE_LIMITED` | 触发限流 |

| 200 + 空集 | — | 查询合法但无匹配（正常业务结果） |

### 3.4 审计日志

每次调用记录：调用方 appKey、来源 IP、时间戳、nonce、查询条件（险种/州/产品/关键词）、匹配保司数与产品数、耗时、返回码。不记录客户 PII（也不接收）。日志保留期限与现有审计日志策略对齐。

### 4.1 `auth_user` 表变更

## 六、待与 workOS 方对齐事项

1. code 换发接口规格：URL、请求凭证（client_id/secret 如何发放）、code 有效期、响应字段、错误码；
2. 用户同步：实时单条是否满足，是否需要定时批量对账接口；工号生成与稳定性规则；
3. 角色目录：以子系统提供的角色 key 为准，权限目录的获取方式（建议接口动态获取 + 文档双保险）及变更通知机制；
4. HMAC 签名细节确认：签名串拼接顺序、编码、header 命名（以本规格草案为基础确认）；
5. workOS 出口 IP 网段清单与变更通知流程；
6. 离职/转岗时效：状态同步到子系统的延迟要求，是否必须即时吊销在线会话；
7. 部署形态：两个子系统对外暴露的域名/网关、是否经统一 API 网关接入；
8. 联调环境：workOS 沙箱地址、测试 appKey/Secret、测试工号。

## 七、非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | 密钥密文存储、不落日志；签名校验失败不回传细节；所有集成接口独立鉴权守卫，与人工 JWT 分离 |
| 性能 | 匹配接口 P95 ≤ 800ms（当前数据量级）；支持后续加缓存（保司/产品低频变更，可短 TTL 缓存） |

| 国际化 | 对外接口数据双语返回（name_zh/name_en），不依赖调用方传语言做数据翻译 |
| 兼容 | 本地账号密码登录、现有角色权限体系、现有前端页面均不做破坏性改动 |
| 限流与防护 | 集成接口独立限流；异常调用（连续签名失败）告警与临时封禁策略 |

## 八、验收标准

**模式 A**

1. workOS 跳转带 code 可完成登录，子系统用户表生成/匹配到 `auth_method='sso'`、`sso_provider='workos'`、带工号的账号；
2. 用户菜单与操作权限与同步的角色一致；篡改 URL 注入 role 无效；
3. workOS 推送禁用后，该用户无法登录；未同步工号的 code 换发被拒绝并给出明确提示；
4. SSO 用户无本地密码，密码登录方式对其拒绝；用户列表正确显示 SSO 标识；
5. 本地账号登录、登出、刷新 token 等既有流程无回归。

**模式 B**

6. 合法签名 + 白名单 IP 的匹配请求返回保司/授权产品/核保要点三块数据，双语完整；
7. 过滤口径正确：终止/到期合作、未授权产品、停售产品、未开通州均不返回；
8. 错误签名、过期时间戳、重放 nonce、非白名单 IP、超量请求分别得到对应错误码；
9. 审计日志可查询每次调用的调用方、查询条件与结果数量，且不含客户 PII；
10. 接口不返回渠道、财务/费率、联系人等一期排除数据。

**同步接口**

11. 同一工号重复推送保持幂等；角色 key 非法整单拒绝；`local` 账号不被覆盖；
12. 权限目录接口返回的角色可被 workOS 侧用于授权选择，与子系统实际权限一致。

## 十、一期非目标（明确排除）

1. 渠道商（下游渠道用户）发起的保单咨询；
