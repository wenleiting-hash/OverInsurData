# 文档概述

## 背景与问题

海外保险数字化平台面向**美国（V1.0.3 扩展支持中国）**保险市场，需要同时管理上游保险公司（Carrier）和下游分销渠道（Agency / Broker / MGA / Agent）。当前行业存在以下核心痛点：

- **保险公司主数据分散：**各保险公司的产品、费率、可售州、佣金方案信息散落在 Excel 和邮件中，缺乏统一管理。
- **渠道层级复杂：**美国保险分销体系包含 FMO→Agency→Branch→Agent 多级层级，以及 MGA、Wholesale Broker 等特殊角色，层级关系和佣金分润（Override）计算高度复杂。
- **合规风险高：**美国保险以州为单位监管，业务员必须在每个州持有 License 并获得保险公司的 Appointment 才能出单；渠道机构需持 Business Entity License、E&O 保险、W-9；CE 学时需周期复核；OFAC/SAM.gov 黑名单需月度扫描；Stamping Office 加签需跟踪。
- **佣金结算低效：**佣金规则涉及首年/续年递减、阶梯佣金、Override、Contingent Commission（基于赔付率）、Premium Tax（州×Admitted/Surplus）、退保追回（Chargeback）等多种维度，与保险公司账单对账耗时长。
- **渠道订单缺失（含询价环节）：**V1.0.2 渠道订单未建设，渠道商上报客户询价（Quote）、报价跟进、投保申请等前置环节无系统承载，询价信息散落在线下表格/邮件中，转化率不可见；出单后与保司账单匹配只能手工关联，对账效率低。V1.0.3 本期必须建设渠道订单，且订单起点从渠道商上报客户询价开始，而非出单后补录。
- **业务员层级管理薄弱：**V1.0.2 仅管理"代理人"笼统档案，未细化到 Individual Producer 的 NPN/License States/License LOA/Appointment 列表/CE 学时等美国监管要求字段。
- **政策下发链路缺失：**保险公司费率/核保/产品政策下发无系统化管理，时效无控制，版本替代关系无追踪。
- **多语言协作困难：**平台需同时服务美国本地用户和中国运营团队，双语文档和界面缺失影响协作效率；V1.0.3 需将 businessCountry（US/CN）数据层与语言（中/英）UI 层解耦。

## 产品目标

本平台旨在构建一套覆盖保险公司管理与渠道管理全链路的数字化系统，实现以下目标：

1. **主数据统一：**建立保险公司、产品、渠道、业务员的统一主数据中心，支持多维度关联和实时查询；V1.0.3 引入 businessCountry（US/CN）字段贯穿渠道侧所有主数据。
2. **渠道全生命周期管理：**从渠道档案建立、合作协议签订、Appointment 授权到层级管理、结算支付、退出，全流程线上化；V1.0.3 按 7 大模块重组（档案/合作/授权/培训/合规/结算/政策），入驻/绩效/门户本期移出。
3. **渠道订单与佣金自动化：**V1.0.3 本期建设渠道订单，订单从渠道商上报客户询价（Quote）开始，覆盖询价→报价→投保申请→核保登记→出单回填→账单匹配→佣金自动计算→对账→结算→支付全链路；询价与投保前置环节本期以登记制承载（人工报价/费率档案试算），保司费率引擎 API 开放后升级为实时报价。
4. **合规硬联动+白名单豁免（V1.0.3 恢复）：**恢复渠道合规模块，合规异常自动挂起关联实体（授权/合作/结算），白名单命中则不挂起仅记录；非 V1.0.2 的"移除合规"口径，也非 V1.0.1 的"自动筛查"口径。
5. **业务员 Individual Producer 全字段管理：**NPN、License States、License LOA、Appointment 列表、CE 学时进度、状态机；License 过期自动暂停 Appointment，CE 未达标触发培训任务。
6. **美国保险口径补齐：**Contingent Commission（基于 Loss Ratio 的年度核算）、Premium Tax（州×Admitted/Surplus 代缴配置）、Stamping Office 加签、1099-MISC/1099-NEC 年报。
7. **渠道政策单向发布：**管理我司下发保险公司政策（费率/核保/产品/合规/促销），时效 Permanent/Term，防冲突规则，版本替代关系。
8. **渠道自助服务：**提供业务员门户，支持在线报价、出单、保单管理、佣金查询、培训学习，降低运营成本。
9. **国际化支持：**全平台中英文双语切换，支持中美两地用户高效协作，默认英文符合目标市场；业务国别与语言切换解耦。

### 非目标（Out of Scope）

- **核心保单系统：**本期不包含保单核心系统（承保、理赔、保全）的开发，仅通过 API 与外部核心保单系统集成。
- **费率引擎：**产品定价和费率计算由保险公司核心系统或独立费率引擎负责，本平台仅存储费率档案引用。
- **理赔管理：**理赔报案、查勘、定损、赔付不在本期范围内。
- **客户 CRM：**终端客户（投保人）的完整 CRM 功能不在本期，业务员门户仅包含基础客户信息管理。
- **财务总账：**本平台生成佣金支付指令后，由外部财务系统完成总账记账和支付，本平台不替代财务系统。
- **再保险管理：**再保险合约、分保、赔款分摊不在本期范围。
- **政策双向：**V1.0.3 渠道政策为单向（我司下发保险公司政策），不接收渠道上报。
- **CN 业务完整建设：**V1.0.3 引入 businessCountry 字段与 CN 字段集，但 CN 业务本期仅做字段集预留，完整业务流程建设延后。
- **其他语言扩展：**首期仅支持 en-US + zh-CN，西班牙语等未来扩展预留但不在本期开发。

# 系统整体架构

平台采用分层架构，分为用户层、应用服务层、核心引擎层、数据层和外部集成层。

## 架构设计原则

1. **主数据集中：**保险公司、产品、渠道、业务员四类核心主数据统一存储和管理，作为全平台唯一数据源。
2. **引擎可配置：**佣金规则、核保规则、权限校验规则、合规硬联动规则均通过规则引擎配置，不硬编码，支持业务人员自助配置。
3. **审计可追溯（V1.0.3 强化）：**所有主数据变更、层级调整、佣金方案修改、状态变更、合规事件、白名单操作、政策发布、渠道订单状态流转均记录审计日志，支持全链路追溯。合规事件链路审计不可删除，保留 ≥5 年。
4. **事件驱动：**保单新单/续保/退保/批改等事件通过消息队列驱动佣金计算与合规联动，支持异步处理和重试。
5. **国际化就绪：**前端基于 react-i18next 框架，所有 UI 文案外置为 JSON 翻译文件，支持运行时语言切换；V1.0.3 新增 channel.json 命名空间（ch 前缀），businessCountry（US/CN）数据层与语言（中/英）UI 层解耦。
6. **合规硬联动（V1.0.3 新增）：**合规异常 → 自动挂起关联实体（授权/合作/结算） → 白名单命中则不挂起仅记录 → 推送整改 → 复检通过自动恢复/未通过升级；硬联动规则引擎化配置。

# 核心业务场景

## 场景一：渠道商询价上报、报价出单与合规硬联动

> **本期建设口径（V1.0.3）：**渠道商上报客户**询价订单（Quote Order）**、报价登记与跟进、投保申请、核保进度登记、出单回填、订单全状态流转**本期必须建设**，在渠道订单模块（2.6 独立子模块）中落地；保司 API 未开放前，报价采用"人工报价 / 费率档案试算 + 系统登记"方式（与全域登记制口径一致），保司核心系统/费率引擎的**实时报价 API 调用、自动核保**为未来态。
>
> ⚠️ **未来态部分：**系统直连保司费率引擎获取实时报价、自动核保通过/出单（Bound）依赖保司 API 开放；未来态实现时合规校验采用"硬联动+白名单豁免"口径，而非 V1.0.2 的"线下流程保障"。

**Actor：**渠道商业务员（Individual Producer）、渠道运营/核保协调员、保险公司核心系统（未来态）

**触发：**渠道商业务员获取到客户投保意向，在渠道门户上报客户询价

### 正常流程（询价 → 报价 → 投保 → 核保 → 出单 → 结算）

**阶段一：询价上报（本期，订单类型=Quote）**

1. 渠道商业务员在渠道门户（或运营代录）创建询价订单：选择 Carrier/Product/LOB/State，录入客户基本信息（客户类型 individual/commercial、投保人 Named Insured、联系方式）、被保人、风险地址、按险种录入风险明细（如车险 VIN/车型/年款/驾驶员记录；房屋险建造年份/结构/保额意向）、保障意向（Coverage Requested）。
2. 系统执行前置校验三件套（产品可售州 ∩ 渠道持牌州 ∩ 合作协议有效期）与 6 开关之"可报价（can_quote）"校验；校验不通过则不允许提交询价（白名单仅作用于合规事件，不放开授权开关）。
3. 询价订单提交，状态 草稿（DRAFT）→ 询价已上报（QUOTE_SUBMITTED）。

**阶段二：报价（本期登记制 / 未来态实时化）**

4. 当前（保司无 API）：渠道运营/业务员依据保司费率档案试算或线下向保司获取报价后，在系统登记报价结果——报价编号（Quote Number）、报价保费（Quoted Premium）、保费明细（费率/折扣/Premium Tax 与 Policy Fees 预估）、报价有效期（Quote Valid Until，通常 30 天），状态→已报价（QUOTED）；支持多产品报价对比与多次重新报价（Re-quote，quote_version 递增）。
5. 未来态：系统调用保司费率引擎 API 实时返回报价，本步骤自动完成。

**阶段三：报价确认与投保申请（本期）**

6. 客户接受报价的，业务员在门户确认报价（状态→QUOTE_ACCEPTED），完善客户信息、上传核保资料、受益人信息、合规告知确认、电子签名，提交投保申请（状态→APPLICATION_SUBMITTED→UNDERWRITING）。
7. 询价订单在确认后生成转化关系（parent_order_id 关联），出单成功后转化为 New Business 订单。

**阶段四：核保（本期登记 / 未来态自动化）**

8. 当前：核保进度与结果由业务员/运营线下跟进后在系统登记（自动核保通过 / 人工核保中 / 加费协商 / 拒保）；未来态：核保结果由保司核心系统自动同步。
9. 合规校验由硬联动规则保障：业务员 License × Appointment × CE 学时 × 产品可售州 × 产品授权（6 开关"可出单 can_bind"）× 出单限额 × E&O 有效性。

**阶段五：出单（Bound）**

10. 保司出单后回填保单号（Policy Number）、Binder 号、Effective/Expiration Date、最终保费，状态→已成交（BOUND）；订单类型由 Quote 转化为 New Business，触发佣金计算事件，订单进入"已绑定（账单匹配）→待结算→已结算"后段流程（见场景二）。

### 异常与边界

- **前置校验不通过：**产品在该州不可售、渠道合作协议失效、或"可报价"开关关闭的，不允许提交询价订单，系统提示具体原因。
- **报价失效：**超过报价有效期（Quote Valid Until）客户未确认的，状态自动转为 QUOTE_EXPIRED；客户仍有意向的需重新报价（Re-quote，生成新版本报价）。
- **客户撤回：**客户放弃投保的，业务员可撤回询价，状态→QUOTE_WITHDRAWN；询价订单及其报价记录保留可审计，不进结算。
- **出单超限：**保费超过业务员出单限额的，自动转人工核保登记，或提示业务员联系上级提升限额（子渠道限额 ≤ 父渠道限额）。
- **核保加费：**保司核保要求加费的，系统登记加费金额并通知业务员，业务员确认客户接受后继续出单，客户拒绝则询价订单关闭（不进结算）。
- **核保拒保：**保司拒保的，系统记录拒保原因（DECLINE_REASON）并通知业务员，订单状态→已拒保（DECLINED，终态，不进结算）。
- **合规硬联动拦截：**业务员 License 过期 / Appointment Withdrawn/Revoked / CE 未达标 / E&O 过期时，硬联动规则自动挂起业务员 Appointment 与产品授权，询价后的报价确认、投保、出单各环节均被拦截；白名单命中则不挂起仅记录。
- **数据边界：**询价阶段客户 PII 最小化采集（承保必需字段），SSN Last 4 等敏感信息仅在投保申请阶段采集并加密存储。

## 场景二：佣金计算与结算（V1.0.3 渠道订单+四段式流转）

**Actor：**系统佣金引擎、佣金财务、业务员

**触发：**结算周期到达（月度/季度）

### 正常流程（资金四段式流转）

1. **第一段：客户向保司投保付款**——客户通过业务员向保险公司投保并支付保费。
2. **第二段：保司返点给我司（上游对账，属保司模块）**——保司按协议佣金率返点给我司，我司导入保司账单→批次对账→差异处理（属保险公司财务与结算模块）。
3. **第三段：我司付渠道佣金（下游结算，属渠道模块）**——我司按渠道合作协议佣金率付给渠道：
   - 3.1 结算周期到达，系统自动触发佣金计算任务。
   - 3.2 数据采集层采集本周期**已成交（BOUND）渠道订单**（New Business/Renewal/Endorsement/Cancellation/Reinstatement；询价 Quote 及失效/撤回/拒保订单不采集、不进结算）、保司账单匹配结果、渠道层级快照、佣金方案配置、Contingent Commission 配置、Premium Tax 配置。
   - 3.3 逐单计算层按多维规则匹配佣金方案，计算直接佣金；Surplus Lines 业务同步计算 Premium Tax 代收代缴金额。
   - 3.4 层级汇总层沿层级树向上遍历，逐级计算 Override 佣金。
   - 3.5 调整层处理退保追回（Chargeback）、阶梯回溯调整、人工调整、预支抵扣。
   - 3.6 按业务员/机构汇总当期净额，生成佣金结算单（含 Premium Tax 代缴明细）。
   - 3.7 佣金财务审核结算单，大额需总经理加签。
   - 3.8 审批通过后生成支付指令，通过 ACH/支票/电汇完成支付。
   - 3.9 支付结果回写，业务员可在门户查看佣金到账。
4. **第四段：渠道收到佣金**——渠道/业务员收到我司支付的佣金。

### 异常与边界

- **退保追回：**保单在追回期限内退保的，系统自动计算应追回金额，从当期佣金中抵扣；当期不足的结转下期，超过结转期限转坏账。
- **对账差异：**渠道订单与保司账单匹配不一致的，标记差异，财务人工核查后调整或向保险公司追讨；差异类型（金额/归属/险种/时效）自动分类。
- **计算失败：**佣金计算任务失败的，系统自动重试 3 次，仍失败的通知技术团队排查，支持手动触发增量/全量重算。
- **负佣金余额：**追回金额大于当期佣金时，业务员佣金余额为负，系统展示待抵扣金额，不产生支付。
- **Contingent Commission 年度核算：**保司年度 Loss Ratio 达标时触发 Contingent Commission 计算，按配置比例年度结算，单独生成结算单。
- **Premium Tax 代缴差异：**Surplus Lines 业务 Premium Tax 代收代缴金额与保司账单不一致的，按州核查代缴方与税率配置差异。

## 场景三：渠道合规硬联动+白名单豁免（V1.0.3 新增）

**Actor：**系统合规引擎、渠道合规专员、渠道运营

**触发：**每日扫描 / 临期触发 / 业务员 License 状态变更

### 正常流程

1. 系统每日扫描所有合作中渠道的资质（Business Entity License/E&O/W-9/Individual Producer License×州×LOA/Appointment 状态/CE 周期/FEIN/OFAC/SAM.gov/Stamping Office 加签/背景调查有效期）。
2. 发现合规异常（如业务员 License 过期），系统自动挂起关联实体：
   - 挂起该业务员所有 Appointment（状态=暂挂）。
   - 挂起该业务员所有渠道授权（6 开关全部置灰）。
   - 挂起该业务员所在渠道的当期结算（暂停支付）。
3. 系统检查白名单（渠道×监测项×豁免期）：
   - 命中白名单：不挂起，仅记录合规事件（豁免理由、豁免期、审批人、附件）。
   - 未命中白名单：维持挂起状态。
4. 系统推送整改任务给渠道主联系人与我司运营。
5. 渠道完成整改（如 License 续期），上传新资质文件。
6. 系统复检通过：自动恢复 Appointment、授权、结算；复检未通过：升级处理（终止合作/上报监管）。
7. 所有合规事件（发现、挂起、白名单命中、整改、复检、恢复/升级）全链路审计，不可删除，保留 ≥5 年。

### 异常与边界

- **白名单滥用：**白名单豁免需审批，有效期不超过 90 天，到期自动重新评估。
- **复检超时：**整改任务超时未完成的，系统自动升级处理（终止合作）。
- **OFAC/SAM.gov 命中：**直接拒绝合作，不可白名单豁免。
- **多业务员同时异常：**仅挂起异常业务员关联实体，不影响同渠道其他业务员正常业务。

## 场景四：渠道政策单向发布（V1.0.3 新增）

**Actor：**渠道政策运营、系统政策引擎

**触发：**保险公司下发政策（费率/核保/产品/合规/促销）

### 正常流程

1. 渠道政策运营录入政策主表：政策类型（Underwriting Guideline / Rate Manual / Product Bulletin / Compliance Bulletin / Carrier Notice）、来源 Carrier、适用 LOB、适用 State、适用渠道（All/Named）、时效（Permanent/Term）、Effective Date、Expiration Date、内容正文+附件（Rate Manual PDF/Underwriting Matrix）。
2. 系统校验防冲突规则：同一产品同一类型政策有效期不可重叠。
3. 政策提交发布审批，审批通过后状态=PUBLISHED。
4. 到达 Effective Date 状态=EFFECTIVE，系统按配置推送通知给受影响渠道。
5. 联动：
   - **产品下架政策** → 自动暂停该产品所有渠道授权。
   - **Rate 变更政策** → 触发结算比例复核（推送财务模块）。
   - **Underwriting 变更政策** → 推送培训任务给相关业务员。
   - **Compliance Bulletin** → 推送合规专员审核。
6. 到达 Expiration Date（Term 类型）状态=EXPIRED；或被新政策 Superseded（替代关系链）。

### 异常与边界

- **政策冲突：**同一产品同一类型政策有效期重叠时，系统拒绝发布，提示冲突政策编号。
- **替代关系链：**新政策发布时可声明 Supersedes 旧政策，旧政策状态自动流转为 SUPERSEDED。
- **Auto-Expire Rule：**Term 类型政策到期前 N 天提醒，到期自动流转 EXPIRED。
- **政策下发不可逆：**已发布政策不可删除，仅可 Withdrawn（撤销）并登记撤销原因。

# 佣金引擎详细设计

## 佣金计算全流程

```
数据采集 → 逐单计算 → 层级汇总(Override) → 调整处理 → 汇总生成结算单
```

**关键特性：**
- 事件驱动（保单事件/渠道订单事件异步触发）
- 快照机制（计算时冻结渠道层级 + 佣金方案版本）
- 增量计算 + 全量重算
- 断点续算
- 规则匹配采用"最具体优先"原则（多维维度权重评分，评分相同取最近更新）

## 规则维度与匹配优先级

佣金规则采用多维矩阵配置，一条规则由以下维度共同确定：

| 维度 | 字段 | 说明 | 是否必填 | 匹配优先级权重 |
| --- | --- | --- | --- | --- |
| 保险公司 | carrier_id | 规则适用的保险公司，空=全部 | 否 | 100 |
| 渠道类型 | channel_type | 规则适用的渠道类型 | 是 | — |
| 渠道层级 | hierarchy_level | 规则适用的层级（用于 Override） | 是 | — |
| 业务线 | line_of_business | 规则适用的业务线，空=全部 | 否 | 20 |
| 产品 | product_id | 规则适用的具体产品，空=全部 | 否 | 50 |
| 州 | state_code | 规则适用的州，空=全部 | 否 | 30 |
| 保单年度 | policy_year | 首年/续年（第 N 年） | 是 | — |
| 缴费方式 | payment_mode | 年缴/半年缴/季缴/月缴 | 否 | 10 |
| 业绩档位 | tier_level | 阶梯佣金的档位 | 否 | 5 |
| 佣金类型 | commission_type | DIRECT/OVERRIDE/RENEWAL/BONUS/CONTINGENT | 是 | — |

**匹配规则：**当多条规则同时匹配时，按"最具体优先"原则，取优先级评分（各维度权重之和）最高的规则；评分相同则取最近更新的规则。

## 佣金类型体系

| 佣金类型 | 英文 | 说明 | 计算基础 |
| --- | --- | --- | --- |
| 直接佣金 | Direct Commission | 业务员销售保单的直接提成 | 保费 × 佣金率 |
| Override 佣金 | Override Commission | 上级对下级业绩的管理津贴 | 下级团队保费 × override 率 |
| 续期佣金 | Renewal Commission | 保单续年的佣金（通常递减） | 续期保费 × 续期佣金率 |
| 服务佣金 | Trail / Service Commission | 长期保单的年度服务佣金 | 有效保费 × 服务费率 |
| 奖金/激励 | Bonus / Incentive | 达到业绩目标的额外奖励 | 按方案计算 |
| MGA 管理费 | MGA / Program Fee | MGA 收取的核保/管理费 | 保费 × 费率 或 固定金额 |
| 或有佣金 | Contingent Commission | 基于赔付率/利润的事后分成（V1.0.3 强化） | 按年度利润计算，Loss Ratio 阈值触发 |
| 退保追回 | Chargeback / Clawback | 退保时追回已付佣金（负佣金） | 已付佣金 × 追回比例 |
| Premium Tax 代缴 | Premium Tax Withholding | Surplus Lines 业务代收代缴保费税（V1.0.3 新增） | 保费 × 州税率（按 Admitted/Surplus） |

## 退保追回 (Chargeback) 规则

| 参数 | 说明 |
| --- | --- |
| 追回期限 | 保单生效后多少个月内退保可追回佣金（如车险 12 个月，寿险 24 个月） |
| 追回方式 | 区间固定比例（如 0-3 月 100%、4-6 月 75%、7-9 月 50%、10-12 月 25%）或按未到期天数比例（Pro-rata） |
| 追回上限 | 单笔最大追回金额 |
| 追回方式 | 从未来佣金抵扣（FUTURE_COMMISSION_OFFSET）或直接开票追回（DIRECT_INVOICE） |
| 结转期限 | 负佣金余额最多结转月数，超期转坏账 |
| 豁免条件 | 免追回的特殊情况（保险公司过错退保、客户搬迁、车辆全损等） |

## Contingent Commission 年度核算（V1.0.3 新增）

| 参数 | 说明 |
| --- | --- |
| Loss Ratio 阈值 | 触发 Contingent 的赔付率上限（如 ≤ 50%） |
| 触发比例 | 达标后额外返点比例（如 2%-5% 浮动） |
| 核算周期 | 年度核算（按保司财年） |

| 数据来源 | 保司年报 Loss Ratio 数据，无 API 时人工录入 |

## Premium Tax 代缴配置（V1.0.3 新增）

| 参数 | 说明 |
| --- | --- |

| 税率 | 各州保费税率（如 CA Surplus Lines 3.5%） |

| 年报 | 1099-MISC/1099-NEC 年报生成 |

```

                                                            未通过 → 升级处理（终止合作/上报监管）
```

**订单状态机（全生命周期）：**

```
[询价前段 — QUOTE 订单，不进结算]
DRAFT → QUOTE_SUBMITTED → QUOTED → QUOTE_ACCEPTED → APPLICATION_SUBMITTED → UNDERWRITING
                          │            │
                          │            ├→ QUOTE_EXPIRED（报价超期未确认，终态）
                          │            └→ QUOTE_WITHDRAWN（客户/渠道撤回，终态）
                          └→ QUOTE_WITHDRAWN（上报后客户放弃，终态）
UNDERWRITING ├→ BOUND（核保通过、保司出单，Quote 转化为 NEW_BUSINESS）
              └→ DECLINED（拒保，终态，不进结算）

[出单后段 — 成交订单]
BOUND → LINKED → PENDING_SETTLEMENT → SETTLED
        ├ 退保：→ CHARGEBACK_PENDING → CHARGEBACK_DONE（终态）
        └ 批改：→ 调整中 → SETTLED（更新保费/佣金金额）

[通用终态]
VOID（错误订单作废，保留记录可审计）
```

# 国际化与多语言支持设计

## 13.1 国际化框架选型

基于项目实际需求和技术评估，选择 **react-i18next + i18next** 作为国际化框架（V1.0.3 沿用 V1.0.2 选型）：

| 维度 | React 生态需求 | react-i18next 适配性 |
| --- | --- | --- |
| 组件级文本 | 需要在 JSX 中显示动态文本 | ✅ t() 函数直接在 JSX 中使用 |
| 命名空间隔离 | 不同模块文案独立管理 | ✅ 支持 namespace 分隔（如 carrier:, finance:, **V1.0.3 新增 channel:**） |
| 动态内容 | Key+ 参数拼接（姓名/州名等） | ✅ $name/$state 插值占位符 |
| 性能优化 | 懒加载减少初始包体积 | ✅ useTranslation + lazy loading |
| 热重载开发 | 翻译更新无需重启开发服 | ✅ 完全支持 |
| TypeScript 支持 | 强类型提示和编译检查 | ✅ @types/i18next+i18next-typescript |

## 13.5 配置文件

### i18next.config.js（V1.0.3 扩展 channel 命名空间）

```javascript
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';

i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    fallbackLng: 'en-US',
    debug: process.env.NODE_ENV === 'development',
    interpolation: { escapeValue: false },
    defaultNS: 'translation',
    ns: ['common', 'carrier', 'channel', 'commission', 'finance', 'error'],
    detector: {
      order: ['localStorage', 'navigator'],
      lookupLocalStorage: 'i18nextLng'
    }
  });

export default i18n;
```

```typescript
localStorage.setItem('i18nextLng', 'zh-CN');
```
