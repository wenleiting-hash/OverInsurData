## 一、需求背景（业务方 2026-09-13 明确）

本模块处理**我方平台与上游保险公司之间**的财务结算，业务链路为：

1. **接入方式**：上游保险公司目前**均未开放 API**，我方只能通过**文件导入**方式取得保司账单（佣金账单、保费账单）；
2. **周期驱动**：按**每个保险公司各自的结算周期**，由系统形成我方口径的**佣金对账单**（我方认定的应付/应收基准）；
3. **账单比对**：将我方对账单与保司导入账单进行逐笔及汇总比对，识别差异并跟进处理；同时独立开展**保费账单**对账；
4. **范围排除**：本期**不涉及我方与渠道（渠道组织/代理人）之间的佣金结算**（第十二章 12.1–12.11 整体不在本期）。

**本迭代目标**：打通「文件上传 → 解析（字段映射）→ 周期对账单生成 → 账单/对账单逐笔比对 → 差异处理 → 对账报告」全链路，数据真实可查、动作可写、写操作有审计，交互符合《通用组件与通用交互规范_V1.0》。

## 二、现状核查结论（2026-09-13 实测）

### 2.1 后端（apps/carrier-service/src/modules/finance）

- `finance.controller.ts`：`@Controller('api/finance')` + JwtAuthGuard，**16 个端点全部 `dto: any`，无 DTO、无审计、分页 size 无白名单**。
- 真实接库（5 张表，容器 OVERINSURDATA，库 overinsur_db），但业务语义大面积是假的：

| 端点/方法 | 现状问题 |
|-----------|----------|
| POST bills/upload | 只接收手工填写的元数据 JSON（file_name/合计值），**不接收文件、不解析**；无字段映射、无错误报告 |
| POST bills/:id/parse | `parseBill` 仅把状态 pending-parse→parsed，**不生成任何 commission_bill_line 明细行**（现 line 表 0 行） |
| POST reconciliation/batch | `batchReconcile` 仅把账单状态翻成 reconciled，**无逐笔比对、不生成 reconciliation_diff**（现 diff 表 0 行） |
| GET settlement-history | 从 commission_bill 状态派生，**method 硬编码 'wire-transfer'、reference_number 恒空**，无真实结算台账 |
| GET premium-reconciliation | 用**佣金账单金额聚合冒充**保费对账；无独立保费导入端点 |
| PATCH diffs/:id/action | 仅 5 态状态机（review/dispute/accept/adjust/waive）+ note，无追讨单/红字/挂起/升级 |
| GET settlement-configs | 操作**第二套配置表** settlement_cycle_config（2 行），与合作模块 carrier_settlement_config（3.4，7 行）不同构、互不相通 |

- 全库 39 张表中**没有保单、报价单、保费、期望佣金等交易类表**（仅有主数据/合作/合规/财务账单），`commission_bill_line` 虽预留了 our_policy_number/our_commission_rate/our_commission_amount/diff_amount/match_status 双侧字段，但**"我方期望值"无任何数据来源**。
- 无 CSV/Excel 解析依赖（carrier-service package.json 仅 multer）；通用上传端点 `/api/uploads` 已支持 .csv/.xls/.xlsx 落盘（20MB 限制），可复用但不含解析。

## 五、技术方案（按第四章冻结决策编制）

### 5.1 数据模型（迁移 SQL：ovwr-migration-finance-v1013.sql）

1. `commission_bill` 扩展：`category` varchar(16) 默认 'commission'（commission/premium）、`source_url`/`source_stored_name`（归档原件）、`mapping_template_id`、`import_stats` jsonb（total/imported/failed/skipped）、`period_month` char(7)（YYYY-MM，现 period 文本保留）；因取消解析环节，状态枚举收敛为 `uploaded/reconciled/exception/settled`（现 2 行现值先查后归一，旧 pending-parse/parsed 统一归 uploaded）。
2. 新建 `bill_field_mapping_template`（template_id/insurer_id/category/template_name/file_format/mapping_json 系统字段↔列名/起始行/工作表名/enabled + 审计列）。
3. 新建 `commission_statement`（我方对账单头：statement_id/insurer_id/period_month/category/status(draft/confirmed)/source(import/manual)/source_url/总保费/总佣金/行数/confirmed_by/confirmed_at + 审计列）与 `commission_statement_line`（statement_line_id/statement_id/policy_number/npn/product_code/channel_name/state/lob/premium/commission_rate/commission_amount/adjusted 标记 + 审计列）。
4. `commission_bill_line` 沿用现有双侧列；补 `category` 冗余、`npn`、`product_code`、`row_error`（行级校验错误文本）、`raw_row` jsonb；**入库即终态，无 match_status 解析流转**（匹配结果在对账 run 时计算，不做行级持久化）。
5. 新建 `reconciliation_run`（run_id/insurer_id/period_month/category/statement_id/bill_ids jsonb/status(running/done)/汇总 total/matched/diff/unmatched/差异金额/created_by/confirmed_at/report_json + 审计列）。
6. `reconciliation_diff` 扩展：`category`、`run_id`、`diff_type` 枚举（rate/premium/agent/policy-missing/extra/missing/manual）、`resolution`（open/accepted/adjusted/disputed/suspended/closed）、`follow_ups` jsonb 时间线 [{at,by,note}]；现 status 列数据迁移到 resolution（旧 under-review/disputed/accepted/adjusted/waived 映射 open/disputed/accepted/adjusted/closed）。
7. 新建 `insurer_finance_profile`（1:1 carrier_settlement_config 扩展：config_id 主键关联/next_due_date/next_due_amount/ytd_settled/bank_account/routing_number/contact_email/notify_days_before/min_settle_amount/auto_reconcile + 审计列）；settlement_cycle_config 现有 2 行按 insurer_id 对齐迁入 profile 后该表停用（保留不删，代码不再读写）。
8. 金额一律 numeric(14,2)，比率 numeric(8,4)；所有新表 deleted/created_at/updated_at 三件套。

### 5.2 后端（finance 模块改造 + dtos/）

- **DTO**：BillImportConfirm（含 rows[]）/MappingTemplateUpsert/StatementImport（含 rows[]）/StatementConfirm/ReconcileStart/DiffAction/DiffFollowUp/FinanceProfileUpsert 等；全局 whitelist+forbidNonWhitelisted，rows 单批上限 20000。
- **文件归档与导入**（5.1，无解析环节）：
  - 原始文件复用既有通用端点 `POST /api/uploads`（multipart，已允许 .csv/.xls/.xlsx，20MB 上限），返回 url/storedName；**不新增后端解析代码、不加 npm 解析依赖**；
  - 新增 `POST /finance/bills/import`：前端把 xlsx 在浏览器读取、列映射后的 rows 连同 insurer_id/period_month/category/file_format/source_url/template_id 一次性提交；后端逐行校验（必填保单号、金额非负、枚举合法），全量事务入库 bill + bill_line；返回 {bill_id,total,imported,failed,skipped,errors:[{row,field,message}]}；错误行不阻塞整批（错误计入 errors，不产生脏行）；
  - `GET /finance/bills/:id/errors` 返回错误明细（前端可转 CSV 下载）；映射模板 CRUD（GET/POST/PUT/DELETE /mapping-templates，按 insurer_id+category 列出）。
- **对账单与对账引擎**（5.3）：
  - `POST /finance/statements/import`（rows 同套校验，status=draft）、`PUT /finance/statements/:id/lines/:lineId`（手工调整金额/费率，记 adjusted=TRUE）、`POST /finance/statements/:id/confirm`（draft→confirmed）；

## 八、风险与约束

- **期望值口径风险**：逐笔比对的「期望值」来自导入的我方对账单（非系统自动计算）；若后续要求系统自动计算，依赖保单/佣金计算域（第十二章 12.1）先建成，需重新立项；
- xlsx 0.18.5（SheetJS 社区版）已在前端依赖中，锁定该版本；浏览器端读取大文件占内存，单文件上限 20MB/2 万行，超限前端拦截；账单数据仅在浏览器内存中处理，提交走既有鉴权通道；
- 保司账单格式每家不同，首版覆盖种子中 1–2 种样例模板，其余靠可配置映射兜底；样例文件放 seed-data/samples/；
- 双配置表迁移前先备份两表现值，迁移 SQL 幂等可回滚；合作模块 carrier_settlement_config 写路径不改；
- 浏览器 E2E 只做轻写（导入/对账/差异动作），破坏性操作（删除模板/配置）不测；测试数据用完恢复基线；
- 全程不提交 git。
