## 一、变更背景

### 1.1 V2.1 存在的问题

V2.1 版本在快速迭代中产生了 **三套冲突的 Drizzle Schema** 和 **三套冲突的 SQL 初始化脚本**：

| 冲突源 | 文件 | 表名 | 主键类型 | 问题 |
|--------|------|------|----------|------|
| Schema 1 | `auth-user-schema-ovwr.ts` | `auth_user` | integer (SERIAL) | 字段最完整，被选为权威基准 |
| Schema 2 | `overinsur-auth.ts` | `auth_user` | varchar(32) | 简化版，auth.service 使用此字段 |
| Schema 3 | `permission-schema-ovwr.ts` | `ovwr_auth_user` | varchar(32) | ovwr_ 前缀，另一套独立定义 |

**直接后果：**
- `auth.service.ts` 查询 `real_name`, `status = '1'`, `user_id` (varchar)
- `user.service.ts` 查询 `name_zh`, `name_en`, `mfa_enabled`, `deleted`, `user_uuid` (varchar)
- 两个 Service 对同一张表使用完全不同的列名和值域，运行时必崩

### 1.2 V2.2 核心决策

1. **单一权威 Schema**：以 `auth-user-schema-ovwr.ts` V5 为唯一基准
2. **删除冲突文件**：移除 `overinsur-auth.ts` 和 `permission-schema.ts`
3. **统一主键策略**：`integer id` (SERIAL) + `user_uuid` (VARCHAR 36) 双键
4. **统一状态枚举**：`active` / `inactive` / `locked` / `pending` (varchar 16)
5. **统一 SQL 脚本**：合并为 `seed-data/auth-init.sql`

## 四、账户安全策略

### 4.1 登录失败锁定

```
失败次数 < 5   → 正常提示"用户名或密码错误"
失败次数 >= 5  → 账户锁定 30 分钟，status 改为 'locked'
锁定到期       → 自动解锁（下次登录时检测 locked_until）
```

### 4.2 密码策略

- 加密算法：bcrypt (saltRounds = 10)
- 最短长度：6 位（class-validator @MinLength(6)）
- 密码重置：同时禁用 MFA、清除活跃 refresh token

### 4.3 JWT Token 配置

| 参数 | 值 | 环境变量 |
|------|-----|----------|
| Access Token 有效期 | 1h | JWT_ACCESS_EXPIRY |
| Refresh Token 有效期 | 7d | JWT_REFRESH_EXPIRY |
| 签名算法 | HS256 | — |
| Payload 字段 | userId, username, email, roles[], authMethod | — |
