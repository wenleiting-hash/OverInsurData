## 一、项目定位与业务架构

### 1.1 业务定位

本平台定位于**美国保险市场的中间平台**（MGA/聚合平台模式），核心价值链路为：

```
保险公司（上游） → 我司（平台方） → 渠道合作商（下游）
```

**三方关系明确：**

| 关系层级 | 方向 | 核心内容 |
|---|---|---|
| 上游合作 | 我司 ↔ 保险公司 | 签约、合同、结算参数、对接人、续约、产品资源接入 |
| 中间授权 | 保险公司产品 → 我司 → 渠道 | 产品接入、对渠道授权、出单权限与限额 |
| 下游管理 | 我司 ↔ 渠道 | 入驻、层级、佣金、绩效、培训、门户 |

> **说明：** 保险公司管理为我方纯内部管理，上游保司均未开放API，数据靠人工录入/文件导入，全域无审批流（登记制+审计日志）。

### 1.2 平台核心价值

- 从保险公司获取产品资源和出单权限
- 精细化授权给下游渠道使用
- 实现佣金自动化计算和结算
- 确保出单合规（8步校验链路）

### 1.3 行业痛点（项目背景）

| 痛点 | 描述 |
|---|---|
| 保险公司主数据分散 | 产品、费率、可售州、佣金方案散落在 Excel 和邮件中 |
| 渠道层级复杂 | FMO→Agency→Branch→Agent 多级层级，Override 分润计算复杂 |
| 合规风险高 | 州级监管，代理人需持牌 + Appointment 才能出单，人工校验易遗漏 |
| 佣金结算低效 | 首年/续年递减、阶梯佣金、Override、退保追回多维度规则，对账耗时 |
| 渠道入驻周期长 | 多环节审核平均超过 2 周，缺乏线上化流程 |
| 多语言协作困难 | 需同时服务美国本地用户和中国运营团队 |

## 三、技术架构与核心引擎

### 3.1 系统架构原则

| 原则 | 说明 |
|---|---|
| 主数据集中 | 保险公司、产品、渠道、代理人四类核心主数据统一存储管理 |
| 引擎可配置 | 佣金规则、核保规则、权限校验规则引擎化配置，不硬编码。注：核保规则当前为文档化登记，自动执行待保司API开放 |
| 合规前置 | 8步校验独立引擎，报价/出单请求进入核心流程前完成 |
| 事件驱动 | 保单新单/续保/退保/批改事件通过消息队列驱动佣金计算 |
| 审计可追溯 | 所有主数据变更、层级调整、佣金方案修改、状态变更全链路审计 |
| 国际化就绪 | react-i18next 框架，UI 文案外置 JSON 翻译文件，运行时切换 |

### 3.2 佣金引擎（五阶段流水线）

```
数据采集 → 逐单计算 → 层级汇总(Override) → 调整处理 → 汇总生成结算单
```

**关键特性：**
- 事件驱动（保单事件异步触发）
- 快照机制（计算时冻结渠道层级 + 佣金方案版本）
- 增量计算 + 全量重算
- 断点续算
- 规则匹配采用"最具体优先"原则（多维维度权重评分，评分相同取最近更新）

**佣金类型体系：** 直接佣金、Override 佣金、续期佣金、服务佣金（Trail）、奖金/激励、MGA 管理费、或有佣金、退保追回（Chargeback）。

### 3.3 出单合规校验（8步链路）

| 步骤 | 校验项 | 不通过处理 |
|---|---|---|
| 1 | 代理人持牌（NIPR 数据） | 拦截 |
| 2 | 代理人 Appointment | 拦截 |
| 3 | 机构 Appointment | 拦截 |
| 4 | 产品可售州 | 拦截 |
| 5 | 机构产品授权 | 拦截 |
| 6 | 代理人产品授权 | 拦截 |
| 7 | 培训认证 | 拦截 |
| 8 | 出单限额 | 转人工核保或拦截 |

所有拦截事件记录审计日志，不可删除，保留期不少于 5 年。

## 五、核心业务场景

### 场景一：新渠道入驻（7阶段流水线）

```
在线申请 → 资料审核 → NIPR校验+OFAC筛查 → 背景调查 → 合同签署 → Appointment → 账号开通 → 培训认证
```

关键风险点：同一申请累计驳回 >3 次需主管介入；OFAC 确认命中直接拒绝入驻。

### 场景二：代理人报价出单与合规校验【未来态（待保司API开放）】

```
录入客户信息 → 8步合规校验 → 获取实时报价 → 确认方案 → 提交核保 → 出单 → 触发佣金计算事件
```

### 场景三：佣金计算与结算

```
结算周期触发 → 数据采集 → 逐单计算 → Override层级汇总 → 调整处理（追回/阶梯/人工/预支）
→ 生成结算单 → 多级审批（主管→财务→总经理） → 支付（ACH/支票/电汇） → 结果回写
```

## 八、关键风险与建议

### 8.1 高风险项

| 风险 | 影响 | 建议 |
|---|---|---|
| 佣金规则复杂度极高 | 多维匹配+阶梯+Override+追回，测试用例爆炸 | 优先建设规则引擎测试沙盒 |
| 上游保司无API，账单/产品/牌照数据依赖人工录入与文件导入 | 数据质量与及时性风险 | 建立数据校验规则、导入模板规范、双人复核机制 |
| 数据权限模型复杂 | 功能权限×数据权限双重约束，易出越权问题 | 统一权限中间件，避免各模块自建 |
| 合规拦截不可绕过 | 拦截逻辑错误将导致合法出单被误拦 | 需完整的规则测试和豁免机制 |

### 8.2 架构建议

1. **佣金引擎独立服务化** — 计算密集，需独立部署和扩容
2. **合规校验引擎可配置化** — 8 步校验规则应支持热更新
3. **层级关系需快照机制** — 佣金计算时冻结层级，避免调整影响历史
4. **事件驱动架构** — 保单事件→消息队列→佣金计算，解耦核心流程
5. **审计日志统一设计** — 所有实体变更统一走审计中间件

## 九、总结

本项目是一个**高复杂度的 B2B 保险中台系统**，核心难点在于：

1. **佣金计算引擎** — 多维规则匹配 + 层级 Override + 退保追回的叠加复杂度
2. **合规校验链路** — 8 步校验涉及跨系统数据（NIPR/OFAC/培训），实时性要求高
3. **多层级组织架构** — 多上级、按保险公司/业务线分维度汇报
4. **中间授权模式** — 我司作为平台方的"产品接入→授权→出单"链路设计

需求文档功能点定义到操作级（139 个功能点），质量整体优秀，可直接进入技术方案设计和工作量评估阶段。
